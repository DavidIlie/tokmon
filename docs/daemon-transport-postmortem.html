1. Symptom

The dashboard sat on Connection lost - waiting for the local tokmon daemon... while a daemon was listening, healthy, and answering HTTP in under a millisecond. The CLI showed reconnecting - showing last known data. It worked, then one day it did not, with no user-visible change in between.

The reported shape was "randomly breaks". That word turned out to be literally accurate, and the randomness had a specific mechanism - see cause A.

2. What it was not

Two hypotheses were pursued and killed by measurement. Recording them because both were plausible enough to have shipped a wrong fix.

Refuted: load-induced health-probe false negatives

Discovery probes /healthz with hard-coded budgets - 250ms in waitForOwner, 500ms in probeHealth. The theory was that a busy daemon misses those, gets declared dead, and is destructively reclaimed. It would have explained everything, including why a loaded machine made it worse.

4,136 probes, zero over even the tightest budget. Worst sample ever observed was 103ms against a 250ms floor. Load does inflate the tail by ~25x, so the sensitivity is real, but the headroom is about two orders of magnitude. Hypothesis dead.

Refuted: the discovery walk is a multi-second event-loop stall

An automated performance review estimated collectSessionFiles at "0.5-3+ seconds" per tick because it walks directories and stats files strictly sequentially. Measured against a real 2,658-file corpus: 43ms, with 0.0ms of event-loop lag. The pattern was genuinely inefficient and worth fixing, but it was never the outage.

The check that misled the investigation

/healthz was being used as a liveness signal. It is a plain HTTP handler on the same server and says nothing whatsoever about whether the RPC layer works. It answered in 0.4ms throughout, which is exactly why the daemon kept looking healthy while every client was being rejected. Andrei called this out; it was the turning point.

3. Cause A: two RPC dialects Blocking

Instrumenting WebSocket inside the live dashboard produced the actual exchange:

SEND {"_tag":"Request","id":125,"tag":"tokmon.config","payload":{},...}
SEND {"_tag":"Request","id":126,"tag":"tokmon.snapshot","payload":{},...}
RECV {"_tag":"Defect","defect":"Invalid request id: 125"}
SEND {"_tag":"Interrupt","requestId":126}
CLOSE code=1000

...then a new socket, ids 128-130, same rejection. Forever.

The socket upgrades correctly. The very first frame is rejected by the server, the session dies, and the supervisor redials into an identical failure. To a user that is simply "offline".

Why

effect-rpc changed how a request id is encoded on the wire between the two versions present in this repo.

SurfaceeffectRequestIdServer accepts
root: daemon, CLI, and the shared RPC client the dashboard bundles 4.0.0-beta.102id => idnumber, string
src/desktop and web pins 4.0.0-beta.59id => BigInt(id)bigint, string

The dashboard's RPC client is not local to the web package - it imports src/client/daemon-rpc-client.ts from the repo root. Vite resolves that file's effect import from the root node_modules, so the browser bundle shipped beta.102 and sent numeric ids regardless of the beta.59 pin in web/package.json. Meanwhile the desktop app bundled beta.59 for its in-process daemon, whose server rejects numbers.

Why the protocol check did not catch it

TOKMON_PROTOCOL_VERSION = 5 versions the application's own contract. The frame codec underneath it is an unversioned third-party dependency. Both sides validated "protocol 5", agreed, attached, and then failed on the first frame. The compatibility gate was checking the wrong layer.

Where the randomness came from

The daemon is a singleton and either surface can own it. beta.102's server accepts both encodings; beta.59's accepts only its own. So the outcome depended entirely on who won the lock race at startup:

Daemon ownerServerDashboardCLIDesktop client
CLIbeta.102WorksWorksWorks
Desktop appbeta.59RejectedRejectedWorks

Start the app before touching the CLI and nothing works. Run a CLI command first and everything works. Same machine, same versions, opposite outcome - which is what "randomly breaks" actually meant.

4. Cause B: the dashboard had no stable address Contributing

Both spawn paths bound an OS-assigned ephemeral port: daemon-handle.ts:220 passed --port 0, and desktop/main/index.ts:392 passed port: 0. The browser client binds to wherever the page was served from (rpc-client.ts:69, createDaemonRpcClient(window.location.origin)).

The TUI and Electron both re-read the lockfile and follow a daemon that moves. A browser tab has no lockfile access and no discovery mechanism, so every daemon restart permanently orphaned every open tab, and the reconnect supervisor then redialled a dead port forever.

Measured on the real CLI daemon path, before and after:

OLD (--port 0)                      NEW (canonical port)
boot 1 -> http://127.0.0.1:59246    boot 1 -> http://127.0.0.1:4317
boot 2 -> http://127.0.0.1:59249    boot 2 -> http://127.0.0.1:4317

Observed live on the affected machine, the desktop app moved from port 60049 to 64450 across a single restart. This is why race-condition hardening never fixed it: it is not a race, it is an addressing problem.

5. Cause C: the desktop daemon never noticed it lost the lock Contributing

The CLI daemon self-checks every 30 seconds and exits if the lockfile is no longer its own (web/daemon.ts:102). The Electron host, which runs its daemon in-process, had no equivalent - src/desktop/main/index.ts contained zero references to readLock or any interval.

So if anything reclaimed the desktop's lock, Electron kept serving an orphaned HTTP server and running a second data engine indefinitely: two daemons parsing the same logs, clients split across them, config changes landing in one and not the other, and roughly double the CPU. Nothing surfaced it.

6. The fixes

FixAddressesWhere
One effect version across every surface, plus a workspace overrides entry so it cannot drift again Apnpm-workspace.yaml, both package manifests
Fixed per-channel port range - release 4317+, dev 4417+, span 10. The binder and the browser's recovery scan share one constant Bweb/daemon-channel.ts, web/server.ts
Neither spawn path requests an ephemeral port any more Bclient/daemon-handle.ts, desktop/main/index.ts
A stranded tab probes the candidate range and offers the origin it found Bweb/src/lib/daemon-locator.ts
Loopback-scoped CORS on /healthz, which is what makes that probe readable cross-port Bweb/server.ts
30s lock self-check on the Electron host - rejoins the singleton rather than exiting, since it is the menu-bar app Cdesktop/main/index.ts
Query commands compute locally instead of exiting 1 when the daemon is unattachable Acli-command.ts

Why the port range is shared, not just similar

The bind ladder and the browser scan read the same DAEMON_PORT_SPAN constant. If the binder could land outside the range the browser scans, a tab could still be stranded - which is the original bug wearing a different hat. A test asserts the two ranges are identical.

Resource work, kept separate

Framed deliberately as a cost win rather than part of the reliability fix, because the event loop was never the bottleneck:

  • Discovery walked directories and stat'd files strictly sequentially. Bounded fan-out takes a 2,658-file corpus from 43ms to 19ms per pass.
  • data-engine.persist() no longer calls writeFileSync on the event loop.
  • The shard store encoded and stringified every payload twice - once to size it for the LRU, once to write it - and re-encoded on every disk cache hit purely for accounting. Now serialized once.

7. Review findings acted on

Three defects were found in the fix itself before it landed. Two by review agents, one by a test written for the change.

SeverityFindingResolution
High Fixed ports make pre-binding 4317 trivial, and the locator was silently navigating the tab to whatever answered /healthz - a body any local process can forge, since it carries no secret a real daemon could prove with. Auto-navigation removed. The origin is displayed and the user clicks. Verified separately that wsToken never reaches the browser, so nothing could be stolen even so.
High The relocation probe ignored /healthz's channel. Release and dev are separate installations with separate data, and one probe batch spans both ranges, so a dev tab could be offered the release daemon. Candidates must match the tab's channel, derived from its own port.
Medium persist() became fire-and-forget when it moved off the event loop and nothing awaited it, so shutdown could tear the process down mid-write. Engine exposes the in-flight write; shutdown drains it.
Medium --cached exists to avoid a provider scan, but with an empty cache it silently fell through to a full refresh and burned the whole timeout. Reports that there is no cached data instead.
Medium Making walkFiles concurrent made its output order vary run to run. dedupe() is last-write-wins across files and shard eviction follows load order, so identical refreshes could drift. Sorted. Still 19ms, and now deterministic in a way the original sequential DFS was only incidentally.
Security review of the CORS change - what was tried and rejected

The one genuinely new surface is Access-Control-Allow-Origin echoed on /healthz for loopback origins only. Every bypass attempted was rejected by the parser:

http://127.0.0.1.evil.example, http://localhost.evil.example, http://evil.example#@127.0.0.1, http://[::ffff:127.0.0.1], http://0.0.0.0, http://localhost./, userinfo forms, duplicate Origin headers, and null.

Decimal, octal and hex IPv4 forms (http://2130706433, http://0x7f.1) normalize to 127.0.0.1, but that is consistent parsing rather than divergence - a browser normalizes a page served from those addresses the same way, via the same WHATWG algorithm.

Net capability change for a hostile page: none. It could always send this request; the Host guard was never what stopped it reading the reply, and a non-loopback origin still receives no header. /api/data and /api/config remain same-origin only, asserted by a test that sends a valid loopback origin and requires the header to be absent.

8. Verification

  • 718 tests passing - 502 root, 158 desktop, 58 web. Five consecutive clean runs of the full suite to rule out the port contention the fixed-port change introduced into the test suite.
  • Port stability, on the real CLI daemon path: restart the daemon twice, same origin both times. Compared directly against the old --port 0 behaviour in the same script.
  • Both entry points verified independently: launching only the Electron app brings the daemon up on 4317; running only tokmon usage with no app running brings it up on 4317.
  • Live browser check against a real daemon - dashboard reports live with fresh data and no reconnect churn, where the same page against the old build looped Defect plus CLOSE every few seconds.
  • Socket stability: the desktop app holds one connection to the daemon with an unchanged local port across a 15s sample, rather than the constant churn a reconnect loop produces.
Mistakes made during the investigation
  • Pursued the load hypothesis first and reported it confidently before measuring it.
  • Used /healthz as a liveness proxy for the RPC layer, which is what kept the real fault hidden.
  • Wrote a WebSocket test that opened a socket and sent nothing, then read the absence of frames as evidence. An idle RPC socket never receives anything; the test proved nothing.
  • Launched the desktop app from an automation process tree, which made Electron's ProcessSingleton codesign check fail (task_name_for_pid: (os/kern) failure (5)) and the app quit silently. Chased that as an app defect before realising the launch method caused it.
  • Ran build:web before build:cli; tsup's clean: true wiped dist/web, so the first packaged app shipped with no dashboard and served "not found". The package's own build script orders them correctly.
  • asar extract-file writes to the basename in the working directory and overwrote src/desktop/package.json. Restored from the commit.

10. Still open

  • Not upstream yet. Three commits sit on fix/daemon-transport-resilience. Every user running the 0.32.0 app alongside the CLI has cause A.
  • The local build is ad-hoc signed, not notarized. Auto-update will likely refuse to apply a signed release over it. Reinstalling the official release once the fix ships is the exit path.
  • No independent-vendor review. The diff was reviewed by agents of the same vendor that authored it, which does not satisfy the usual bar. Cursor would not authenticate headlessly during this session.
  • The desktop app has no local degraded mode. When refused it retries every 30s showing disconnected, forever. Fixing that means teaching the renderer to render without RPC - deliberately out of scope here.
  • tableSince() returns 0, so every table refresh aggregates all history with no retention window. This is the main driver of the daemon's ~205MB RSS. Capping it changes what history the UI shows, so it is a product decision rather than a bug fix.
